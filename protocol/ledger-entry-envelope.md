# Ledger Entry Envelope

**Status:** Partially implemented — the entry layout and hash described under "Today" are built and covered by conformance vectors; the full envelope under "Proposed" is an open decision.

Every entry on a shard's append-only chain is hashed over a fixed layout, the envelope. This page shows that layout byte by byte, what a node stores and serves, and the shape of a fuller envelope under discussion. It sits beneath [protocol events](./protocol-events.md), which describes the event itself.

## Terms

- **Envelope**: the fixed, generic part of an entry that every node must read to verify it. Its layout and hash are what stay permanent.
- **Payload**: the kind-specific content (`{"display_name":"Alice"}`). Free-form JSON, canonicalized (RFC 8785, restricted), and the entry commits to its SHA-256, not its bytes.
- **Layout**: the exact byte order a hash is computed over. A layout is identified by a domain tag and a `u16` version.

## Today: the ledger entry

The chain link is `prev_hash`, and the signed tree head commits to the Merkle root of the entries.

```text
ENTRY HASH = SHA-256( signing bytes )

signing bytes, in order:
┌──────────────────────────────────────────────────────────────────────┐
│ domain tag      "avalon.ledger.entry"      ASCII, no length prefix   │
│ version         u16 big-endian             = the EVENT's own version │
├──────────────────────────────────────────────────────────────────────┤
│ network_id      u32 length + UTF-8         which network             │
│ shard_id        u32 length + UTF-8         which chain               │
│ seq             u64                        position in the chain     │
│ prev_hash       32 raw bytes               link to the previous entry│
│ event_id        16 raw bytes (UUID)                                  │
│ kind            u32 length + UTF-8         e.g. "identity.created"   │
│ issuer          u32 length + UTF-8                                   │
│ subject         u32 length + UTF-8                                   │
│ payload_hash    32 raw bytes               SHA-256(canonical payload)│
│ timestamp       i64 unix microseconds                                │
└──────────────────────────────────────────────────────────────────────┘
   payload  (NOT in the hash directly; committed by payload_hash)
   { "display_name": "Alice" }        <- canonical JSON, may be pruned later
```

- Length prefixes and fixed-width integers mean no field can shift another's boundary: `kind="ab", issuer="c"` hashes differently from `kind="a", issuer="bc"`.
- The entry commits to `payload_hash`, so a row whose payload was pruned or erased still verifies and still sits in the tree.
- `network_id` and `shard_id` bind the entry to one chain; `seq` and `prev_hash` order it.
- The version slot holds the event's own version. The entry layout itself has no version of its own, and a changed field set gets a new tag. Nothing in a stored entry says which layout produced its hash, and no hashed field carries a rules version.
- The conformance vector `ledger-entry-hash.json` gives the exact `signingBytesHex` and `entryHashHex` per case. It is generated by a second, independent encoder, so Rust, C#, and TypeScript are each checked against bytes they did not produce.

### The stored and served form

| Field | Meaning |
| --- | --- |
| `seq`, `event_id`, `kind`, `issuer`, `subject` | Same as the hashed fields |
| `version` | The event version (also the hash's version slot) |
| `event_timestamp` | The instant, floored to microseconds (the hashed value) |
| `payload` / `payload_hash` / `payload_pruned` | Content may be gone; the hash never is |
| `prev_hash`, `entry_hash` | The chain link and this entry's hash |
| `batch_id` | The batch whose tree head covers this entry |
| `chain_intact` | Computed on read: link correct, and content matches when present |

### Other layouts that follow the same recipe

One recipe covers them: `tag | u16 version | fields in a fixed order`, strings and byte strings length-prefixed, keys and hashes raw, integers big-endian. A new field means a new version.

| Layout | Tag | State |
| --- | --- | --- |
| Identity chain event | `avalon.identity.chain_event` | Migrated: layout version 1; identity id as 32 raw bytes, `seq`, optional `prev_hash` (flag byte then 32 raw), event id, `kind`/`issuer`/`subject`, event version `u32`, timestamp micros, payload hash |
| Other signed kinds (`identity.created`, device grant, key revoked, attestation issue/revoke, login, continuation, and others) | `avalon.<area>.<kind>` | Registry in `signing_bytes::tags`; each is a `(tag, u16 version, ordered fields)` layout |
| Signed tree head | `avalon-settlement-sth-v1` | Not yet migrated: older layout (root as hex text, `signing_key_id` not covered) |
| Witness cosignature, node request, shard identity | `avalon-...-v1` | Existing binary layouts, kept as they are |

## Proposed: a full envelope

**Proposed**, not decided and not in the code. This is the shape under discussion in [avalon-protocol #1361](https://github.com/avalon-initiative/avalon-protocol/issues/1361), kept here so options can be compared against something concrete. It separates the layout's version from the event's, declares the rules version the author wrote under, and adds a region old nodes can skip.

```text
┌─ ENVELOPE (frozen position and meaning) ──────────────────────────────┐
│ domain tag       "avalon.ledger.entry"                                 │
│ envelope_version u16        which LAYOUT this is (separate from event) │
│ rules_version    u16/u32    rules the author wrote under               │
│                                                                        │
│ network_id, shard_id, seq, prev_hash, event_id,                        │
│ kind, issuer, subject,                                                 │
│ event_version    u32        version of the PAYLOAD schema for `kind`   │
│ timestamp        i64 micros                                            │
│ hash_algo        u8         tag for the hash used for payload/prev     │
│ payload_hash     32 bytes                                              │
│                                                                        │
│ extensions       count u16, then repeated:                             │
│   ┌ ext_type u16 │ flags u8 (bit0 = critical) │ len u32 │ value ┐     │
│   └───────────────────────────────────────────────────────────┘     │
│   non-critical: hashed and preserved by nodes that do not know it     │
│   critical:     a node that does not know it cannot verify the entry  │
└────────────────────────────────────────────────────────────────────────┘
PAYLOAD  (per kind and event_version; canonical JSON; may be pruned)
```

| Part | What it enables |
| --- | --- |
| `envelope_version` | An old node reads the first bytes, sees a version above its range, and fails closed naming the version it needs. A new node dispatches to the right layout for every old entry forever. |
| `rules_version` | Validity of an entry is decided under the rules it declares, never by when it is seen. |
| `event_version` | Payload schema evolution per kind. A payload change is a new `kind@version`, never an edit. |
| `hash_algo` | A future hash is a new tag on new entries, while old entries keep verifying under the old one. |
| `extensions` | Most envelope additions become ignorable by old nodes. |

What stays impossible, by design: changing the meaning of an entry already on the ledger.

### How a node treats an entry it cannot verify

| Node situation | Behavior |
| --- | --- |
| Understands the layout and rules | Verify, project, serve, cosign |
| Layout understood, `kind@version` unknown | Verify, preserve, mirror, relay; do not project; count it as unprocessed |
| Non-critical extension unknown (proposed) | Verify (the extension is hashed), preserve it byte for byte, ignore its meaning |
| Critical extension or `envelope_version` above range (proposed) | Fail closed: do not store as verified, serve as verified, or cosign; report `upgrade required` with the version needed; keep serving everything earlier |
| A write it cannot process | Reject with a typed error naming the supported range |

How an envelope change reaches the network is drawn in [version rollout](../architecture/nodes/version-rollout.md#rolling-out-an-envelope-change).
